# 写计划详细流程

## Phase 0：文档发现（每次必须先执行）

**在写任何计划之前**，先派 subagent 做文档发现：

1. **搜索相关文档**：读取项目 docs/、README、已有代码中的注释
2. **确认 API 真实存在**：查实际源码确认方法签名、参数、返回值，不凭记忆假设
3. **列出允许使用的 API**：引用具体文档来源
4. **标记反模式**：哪些方法已废弃、哪些参数不存在

**核心原则：** 文档存在 ≠ 已被使用。强制读文档，不凭假设。

## 范围检查

如果需求覆盖多个独立子系统，建议拆成多个计划——每个独立产出可运行、可测试的软件。

## 文件结构映射

定义 task 前先规划文件：边界清晰、一个职责、一起变化的放一起、遵循已有模式。

## 粒度

每个步骤是一个动作（2-5 分钟）：写失败测试 → 运行确认失败 → 写最小实现 → 运行确认通过 → 提交。

## 文档结构

读取 `plan-template.md` 了解计划文档模板。

## 禁止占位符

绝不写：TBD、TODO、"添加适当的错误处理"、"类似 Task N"、描述但不展示代码的步骤。

## Subagent 报告契约

每个 subagent 的回复**必须**包含：

1. **查阅了哪些源**（文件路径/URL，读了什么内容）
2. **具体发现**（API 名/签名/路径，精确到行号）
3. **可复制的代码位置**（参考文件的哪一行到哪一行）
4. **置信度 + 已知缺口**（哪些可能还不确定）

**拒绝没有来源的结论。** 如果 subagent 只说"应该用 XXX 方法"但没给出来源，要求它重新查找。

## 自检清单

1. Phase 0 完成：文档已读、API 已确认存在？
2. 需求覆盖：每个需求能指向一个 task？
3. 占位符扫描：搜索红线模式
4. 类型一致性：后续 task 和前面定义的一致？
5. Subagent 报告：每个发现都有来源引用？
