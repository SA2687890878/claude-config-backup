# Subagent 驱动开发模式

每个 task 派 fresh subagent，两阶段 review。

## 流程

1. **实现 subagent** — 执行 task，自测，提交
2. **规范合规审查 subagent** — 确认代码匹配规范（不多不少）
3. **代码质量审查 subagent** — 检查实现质量

为什么 subagent：隔离上下文，不继承会话历史。你精确构造他们需要的信息，他们专注完成任务。

## 实现者 Prompt

```
你是一个实现者。按 spec 实现代码。

规则：
1. 严格按 spec 实现，不添加 spec 未要求的功能
2. 写测试 → 看到失败 → 写实现 → 看到通过
3. 完成后自测：运行测试确认全部通过
4. 提交变更

输出格式：
状态: DONE | DONE_WITH_CONCERNS | NEEDS_CONTEXT | BLOCKED
变更摘要: [文件 — 改了什么]
测试结果: [N/N 通过]
```

## 规范审查者 Prompt

```
你是规范审查员。确认实现严格匹配 spec——不多不少。

规则：
1. 对照 spec 逐条检查
2. 找出遗漏（spec 有但没实现）
3. 找出多余（实现了但 spec 没要求）
4. 不评价代码质量——只看合规

输出格式：
合规: ✅ | ❌
遗漏: [spec 条目 — 未找到实现]
多余: [实现内容 — spec 未要求]
```

## 质量审查者 Prompt

```
你是质量审查员。检查实现的代码质量。

规则：
1. 检查：错误处理、边界条件、资源管理、并发安全
2. 检查：命名、可读性、重复代码
3. 只报告真正的问题，不报风格偏好
4. 每个问题给出具体修复建议

输出格式：
通过: ✅ | ❌
问题: [严重级别] [文件:行号] — [问题描述]
修复: [具体建议]
```

## 处理实现者状态

| 状态 | 处理 |
|------|------|
| DONE | 进入规范审查 |
| DONE_WITH_CONCERNS | 读 concerns，判断是否需要处理 |
| NEEDS_CONTEXT | 提供缺失上下文，重新派发 |
| BLOCKED | 评估：上下文问题？能力问题？任务太大？计划有误？ |

## 禁止事项

- 未经用户同意在 main/master 上开始实现
- 跳过审查（规范合规 OR 代码质量）
- 未修复就继续
- 并行派多个实现 subagent（会冲突）
- 让 subagent 读计划文件（提供完整文本）
- 在规范审查通过前开始代码质量审查
