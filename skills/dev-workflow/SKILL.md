# 开发工作流

## 路由

| 意图 | 分支 |
|------|------|
| 写实现计划（"写计划"、"做个计划"、"plan"） | → A. 写计划 |
| 执行已有计划（"执行计划"、"按计划开发"） | → B. 执行计划 |
| 并行解决独立问题（"并行"、"同时处理"、多个独立 bug） | → C. 并行派发 |
| 不确定 | → 问用户 |

---

## A. 写计划

产出全面的实现计划，假设执行者对代码库零上下文。DRY. YAGNI. 频繁提交。

### 范围检查

如果需求覆盖多个独立子系统，建议拆成多个计划——每个独立产出可运行、可测试的软件。

### 文件结构映射

定义 task 前先规划文件：边界清晰、一个职责、一起变化的放一起、遵循已有模式。

### 粒度

每个步骤是一个动作（2-5 分钟）：写失败测试 → 运行确认失败 → 写最小实现 → 运行确认通过 → 提交。

### 文档结构

读取 `references/plan-template.md` 了解计划文档模板。

### 禁止占位符

绝不写：TBD、TODO、"添加适当的错误处理"、"类似 Task N"、描述但不展示代码的步骤。

### 自检

1. 需求覆盖：每个需求能指向一个 task？
2. 占位符扫描：搜索红线模式
3. 类型一致性：后续 task 和前面定义的一致？

---

## B. 执行计划

### 加载并审查

读取计划文件 → 批判性审查 → 有问题在开始前提出 → 没问题创建 TodoWrite 继续。

### 执行 Tasks

逐 task：标记 in_progress → 严格按步骤执行 → 运行验证 → 标记 completed。

**连续执行：** 不要在 task 之间暂停。只有 BLOCKED、歧义、或全部完成才停下。

### 停下求助

碰到阻塞（缺失依赖、测试失败、指令不清）立即停下。宁可问也不要猜。

### Subagent 模式

对每个 task 派 fresh subagent + 两阶段 review。读取 `references/subagent-pattern.md` 了解详细流程。

**连续执行：** 不要在 task 之间暂停检查用户。只有 BLOCKED 无法解决、歧义阻止进展、或全部完成才停下。

### 模型选择

| 任务类型 | 模型 |
|---------|------|
| 机械实现（1-2 文件，清晰 spec） | 快速模型 |
| 集成和判断任务（多文件协调） | 标准模型 |
| 架构、设计、审查 | 最强模型 |

---

## C. 并行派发

每个独立问题域一个 agent，并发执行。

### 识别独立域

按故障分组。用当：3+ 测试文件因不同根因失败、无共享状态。不用当：故障相关、需要完整系统状态。

### 派发

每个 agent 得到：具体范围 + 明确目标 + 约束 + 预期输出。用 Agent 工具并行派发。

### 集成

agent 返回后：读摘要 → 验证不冲突 → 运行完整测试 → 集成变更。
