# 生成提交信息详细流程

## Step 1: 收集变更

```bash
rtk git status
rtk git diff --cached --stat
rtk git diff --stat
```

- 如果有未暂存的变更，询问用户是否要 `git add`
- 如果没有变更，告知用户"没有需要提交的变更"

## Step 2: 分析变更内容

读取 diff 内容，判断：

| 变更类型 | 判断依据 | 对应类型 |
|---------|---------|---------|
| 新增文件/功能 | 新文件、新接口、新功能 | `新增` |
| Bug 修复 | 修复错误、异常处理 | `修复` |
| 文档变更 | .md 文件、注释、README | `文档` |
| 代码重构 | 重命名、结构调整、不改功能 | `重构` |
| 性能优化 | 算法优化、缓存、减少查询 | `优化` |
| 测试代码 | 测试文件、测试数据 | `测试` |
| 配置变更 | .json/.xml/.yml、依赖、构建 | `配置` |
| 代码回滚 | git revert、回退版本 | `回滚` |

## Step 3: 生成提交信息

格式：
```
[类型] 简短描述（5~100 字符）

详细描述（至少 10 个字符，说明改了什么、为什么改）

关联 Issue #编号（如果用户提到了 issue）
```

### 规则

1. **类型**必须是：`新增`、`修复`、`文档`、`重构`、`优化`、`测试`、`配置`、`回滚`
2. **简短描述**：用中文，动词开头，说清楚做了什么
3. **详细描述**：至少 10 个字符，说明具体改了什么、为什么改
4. **不要**用英文、不要加 scope（如 `feat(api):`）、不要超过 100 字符

### 正文判断逻辑

**只在"为什么改"不明显时才写正文。** 如果简短描述已经说清楚了原因，就不需要正文。

**必须写正文的场景：**
- 破坏性变更（Breaking change）
- 安全修复
- 数据迁移
- 回滚之前的提交

**不需要正文的场景：**
- 简单 bug 修复（原因显而易见）
- 新增文件/功能（描述已足够）
- 配置变更
- 文档更新

### 禁止项

以下内容**绝不**出现在提交信息中：
- AI 署名（"Generated with Claude Code"、"Co-Authored-By: Claude"）
- 复述 diff 内容（"修改了 X 文件"——diff 本身已经说明了）
- 废话开头（"本次提交"、"我"、"我们"）
- 无意义填充（"优化了代码"但不说优化了什么）
- Emoji（除非项目约定要求）

### 示例

```
[新增] 增加用户登录功能

实现手机号+验证码登录方式，对接短信服务商接口，增加登录态缓存逻辑。

关联 Issue #245
```

```
[修复] 修复订单金额计算精度丢失问题

原因为浮点数直接相乘导致精度丢失，改用 decimal 库进行金额运算。

关联 issue #178
```

## Step 4: 确认并执行

展示生成的提交信息，询问用户：
- 直接使用？
- 需要修改？

确认后执行：
```bash
rtk git commit -m "[类型] 简短描述" -m "详细描述"
```

## 特殊情况

- **多个类型**：以主要变更为准。如果改了 5 个文件其中 4 个是修复、1 个是配置，类型用 `修复`
- **混合变更**：如果变更内容跨度太大，建议用户拆分提交
- **WIP 提交**：如果用户明确说"先提交一版"，可以用 `[配置] WIP: 功能名称`，但要提醒这不是规范用法
