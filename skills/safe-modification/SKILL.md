# 安全修改规范

遗留代码可以改，但必须评估后改。

## 核心原则

1. **能新增就不改**：能新增方法/类就不改现有的（减少风险）
2. **必须改就评估**：如果功能确实需要动历史代码，完整评估影响后出解决方案
3. **记录改动**：用 `/memory-save` 记录重要改动

## 决策流程

```
需要改旧代码吗？
  ├─ 能用新增解决 → 新增方法/扩展方法（优先）
  └─ 必须改旧代码 → 完整评估影响 → 出解决方案 → 确认后改
```

## 修改前必须做

1. 运行 `codegraph_callers` 查看谁在用这个方法
2. 运行 `codegraph_impact` 查看改了会影响什么
3. 确认调用方有哪些
4. 确认改动是否会影响其他模块
5. 确认是否需要同步修改调用方
6. 确认改动后如何验证（回归测试）

## 修改方案模板

```
【影响分析】
- 直接调用方：X 个
- 间接影响：Y 模块
- 风险等级：高/中/低

【修改方案】
- 改什么：具体方法/类
- 怎么改：改动内容
- 如何验证：验证步骤

【回滚方案】
- 如何回滚：git checkout 或备份
```

## 不要做的

- ❌ 直接改旧代码不评估
- ❌ 说"不能改"（可以改，但要评估）
- ❌ 说"应该没问题"（要验证）
