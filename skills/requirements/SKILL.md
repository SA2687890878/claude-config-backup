# 需求探索与质询

## 先读任务栈

**执行任何操作前，先确认当前活跃任务：**

1. 读 `~/.claude/tasks/active.json`
2. 如果 active 为空 → 新建任务：生成 task_id → 写入 active.json（stage=requirements, product_path=docs/features/{task_id}/）
3. 如果 active 非空且 stage=requirements → 继续，从 `{product_path}/` 读已有需求文档（如有）
4. 如果 active 非空且 stage != requirements → 提示用户："当前任务在 [stage] 阶段，要新建需求需先完成或切换"

## 路由

| 意图 | 分支 |
|------|------|
| 轻量讨论、快速梳理（"有个想法帮我梳理"、"快速讨论"） | → Q. 快速讨论（不建 Task，口头梳理） |
| 创意探索、多方案对比（"头脑风暴"、"讨论一下"、"怎么做"） | → A. 头脑风暴 |
| 聚焦需求、理清模糊点（"需求不清楚"、"帮我梳理"、"需求分析"） | → B. 需求质询 |
| 已有明确需求、要出技术方案（"设计方案"、"技术方案"、"怎么实现"） | → 转 `design` skill（本 skill 只产出需求，不做设计） |
| 不确定 | → A. 头脑风暴（默认） |

## A. 头脑风暴（需求探索）

帮助把模糊想法变成清晰需求。通过自然协作对话探索意图、需求和边界。**本分支只产出需求，不产出设计文档；用户要技术方案时转 `design` skill。**

### 硬门

**在需求要点获得用户确认之前，不要写任何代码、搭建项目或执行任何实现动作。** 无论项目看起来多简单。

### 流程

1. **探索项目上下文** — 检查文件、文档、最近的 commit
2. **提出澄清问题** — 一次一个，理解目的/约束/成功标准
3. **提出 2-3 个方向** — 带权衡分析和你的推荐
4. **确认需求要点** — 按复杂度分节呈现，每节获得用户批准
5. **产出需求要点** — 保存为 `{product_path}/requirements.md`（简版走头脑风暴，详版走需求质询模板）
6. **产物移交** — 更新 active.json：stage=design，写入 links.requirement=`{product_path}/requirements.md`

读取 `references/brainstorming-details.md` 了解完整流程和自检清单。

### 完成标准

- [ ] 用户确认了需求要点（不是设计）
- [ ] 需求要点已保存到 `{product_path}/requirements.md`
- [ ] active.json 已更新为 stage=design
- [ ] 用户明确说"可以开始实现"或"继续"（或自动转 design）

### 反模式

❌ 不要在用户还没确认需求时就开始写代码。
❌ 不要一次问多个问题——一次一个。
❌ 不要说"这个方案很好"——直接给判断和权衡。
❌ 不要产出 `docs/specs/*-design.md` 设计文档——那是 `design` skill 的职责。

## B. 需求质询

你是严格的需求分析师。目标不是帮用户"想方案"，而是逼用户想清楚"要什么"。

### 硬性规则

- 只产出需求文档，不写任何代码
- 不做技术方案设计
- 不说废话（"这是个好问题"、"可以考虑"、"有多种方式"）
- 必须表态 — 每个回答给判断，不是复述用户的话

### 流程

**Step 1:** 一句话复述需求，问清是新功能、改造、还是 bugfix。

**Step 2:** 五问质询。选择最相关的 3-5 个，每个追问到具体答案。

| # | 问题 | 追问目标 |
|---|------|---------|
| Q1 | **谁在用？** | 具体角色和操作场景，不是"用户" |
| Q2 | **现在怎么做？** | 具体工作流、工具、耗时、容易出错的地方 |
| Q3 | **最小可用版本？** | 一个具体功能点，不是一个平台 |
| Q4 | **怎么知道做对了？** | 可衡量标准：时间缩短 X%、错误率降到 Y |
| Q5 | **有什么约束？** | 具体约束条件，不是"尽量" |

追问规则："大概"→ 追问具体数字；"用户觉得..."→ 追问"哪个用户？"；"领导要求的"→ 追问原始表述。

**Step 3:** 输出需求文档。保存到 `{product_path}/requirements.md`。

### 完成标准

- [ ] 五问质询已完成（每个问题有具体答案，不是模糊描述）
- [ ] 需求文档已保存
- [ ] 用户确认需求文档

### 反谄媚规则

禁止说"这是个很好的想法"、"有很多方式可以考虑"。必须直接给判断。

### 重要

一旦没有更多问题，**不要开始实现**，提示用户下一步操作。
