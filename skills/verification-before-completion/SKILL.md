# 完成前验证

## 概述

在没有验证的情况下宣称工作完成，这不是高效，而是不诚实。

**核心原则：** 始终用证据支撑结论。

**对这条规则敷衍了事，就等于违背了它的精神。**

## 铁律

```
没有新鲜的验证证据，不许宣称完成
```

如果你在这条消息中没有运行验证命令，就不能声称测试通过。

## 门控函数

在宣称任何状态或表达满意之前：

1. **确定**：什么命令能证明这个结论？
2. **运行**：执行完整命令（RTK 自动压缩输出）
3. **阅读**：只看关键行（ERROR/FAIL/exit code），不要读完整输出
4. **验证**：输出是否支持这个结论？
   - 如果否：用证据说明实际状态
   - 如果是：带证据陈述结论
5. **只有这时**：才能做出结论

跳过任何一步 = 说谎，不是验证

## Token 优化验证

构建/测试输出可能很长，用 RTK 压缩：

```bash
# RTK 自动压缩（已配置 hook）
rtk dotnet build
rtk dotnet test

# 只看关键信息：exit code + ERROR/FAIL 行
```

**不要**：读完整构建日志（几十 KB）
**要**：只看 exit code + 错误行（几百字节）

## 常见失败模式

| 结论 | 需要 | 不够格 |
|------|------|--------|
| 构建成功 | `dotnet build` exit 0 | linter 通过、日志看起来没问题 |
| 测试通过 | 测试命令输出：0 failures | 之前的运行结果、"应该会通过" |
| Bug 已修复 | 测试原始症状：通过 | 代码改了，假设已修复 |
| 需求已满足 | 逐项核对清单 | 测试通过 |

## 红线——停下来

- 使用"应该"、"大概"、"似乎"
- 验证前就表达满意（"太好了！"、"完美！"、"搞定！"）
- 即将提交/推送却没有验证
- 信任代理的成功报告
- 依赖部分验证
- 想着"就这一次"
- 累了想赶紧收工

## 防止合理化

| 借口 | 现实 |
|------|------|
| "应该能行了" | 运行验证命令 |
| "我有信心" | 信心 ≠ 证据 |
| "就这一次" | 没有例外 |
| "Linter 通过了" | Linter ≠ 编译器 |
| "代理说成功了" | 独立验证 |
| "部分检查就够了" | 部分检查什么也证明不了 |

## 关键模式

**构建：**
```
✅ [运行 dotnet build] [看到：Build succeeded. 0 Warning(s) 0 Error(s)] "构建通过"
❌ "Linter 通过了"（linter 不检查编译）
```

**测试：**
```
✅ [运行 dotnet test] [看到：Passed! - Failed: 0] "全部测试通过"
❌ "应该能通过了" / "看起来对了"
```

**需求：**
```
✅ 重读计划 → 创建核对清单 → 逐项验证 → 报告缺口或完成
❌ "测试通过了，阶段完成"
```

**代理委派：**
```
✅ 代理报告成功 → 检查 VCS diff → 验证变更 → 报告实际状态
❌ 信任代理报告
```

## 何时使用

**以下情况之前必须使用：**
- 任何形式的成功/完成声明
- 任何满意的表达
- 提交、创建 PR、标记任务完成
- 进入下一个任务

## 底线

**验证没有捷径。**

运行命令。阅读输出。然后才能宣称结果。

这没有商量余地。
