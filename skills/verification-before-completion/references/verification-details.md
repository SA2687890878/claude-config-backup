# 验证详细流程

## 常见验证要求

| 结论 | 需要 | 不够 |
|------|------|------|
| 测试通过 | 测试命令输出：0 失败 | 之前的运行、"应该通过" |
| Linter 干净 | Linter 输出：0 错误 | 部分检查、推断 |
| 构建成功 | 构建命令：exit 0 | Linter 通过、日志看起来好 |
| Bug 修复 | 测试原始症状：通过 | 改了代码、假设修好了 |
| 需求满足 | 逐条检查清单 | 测试通过 |
| Agent 完成 | VCS diff 显示变更 | Agent 报告"成功" |

## 红旗 — 停下

- 用"应该"、"可能"、"看起来"
- 验证前表达满意（"完美！"、"搞定了！"）
- 即将 commit/push/PR 但没验证
- 信任 agent 的成功报告
- 依赖部分验证
- 想"就这一次"

## 防合理化

| 借口 | 现实 |
|------|------|
| "应该没问题了" | 去跑验证 |
| "我有信心" | 信心 ≠ 证据 |
| "就这一次" | 没有例外 |
| "Linter 过了" | Linter ≠ 编译器 |
| "Agent 说成功了" | 独立验证 |
| "我累了" | 疲劳 ≠ 借口 |
| "部分检查够了" | 部分证明不了什么 |

## 底线

**验证没有捷径。** 跑命令。读输出。然后下结论。没有商量余地。

## 冰山法则（关联扫描）

> 修一个 bug → 检查是否是模式。一个问题进，一类问题出。

修复完成后、声称完成前，必须执行关联扫描：

### 扫描范围

| 修复内容 | 扫描对象 |
|---------|---------|
| 修了某个方法的空引用 | 同文件其他方法、同模块类似方法 |
| 修了某个 API 的参数校验 | 同 controller 其他 endpoint |
| 修了某个查询的性能问题 | 同 repository 其他查询 |
| 修了某个组件的样式问题 | 同组件库类似组件 |
| 修了某个配置项 | 同环境其他配置、不同环境的对应配置 |

### 扫描方式

1. **Grep 同类模式** — 用修复中涉及的错误模式搜索代码库
   - 例：修了 `FirstOrDefault()` 后没检查 null → 搜索整个项目同类用法
2. **检查同文件** — 快速扫一遍同文件的其他方法，是否有相同问题
3. **检查同模块** — 检查同一目录/命名空间下的类似实现

### 输出格式

```
关联扫描结果：
- 扫描范围：[具体范围]
- 发现同类问题：[N 个]
  - [文件:行号] 问题描述
- 或：确认无同类问题
```

### 判定

- 发现同类问题 → 必须一并修复（或明确告知用户风险）
- 确认无同类问题 → 可以继续完成声明

这不是"顺便做"。这是验证流程的一部分。修了 A 不查 B，等 B 炸了就是两份复盘。
