# 技术方案设计

把需求文档转成可落地、可验证、可评审的技术方案。

链路：`/requirements`（需求）→ **/design（技术方案）** → `/arch-review`（评审）→ `/dev-workflow`（开发）。

## 路由

| 意图 | 分支 | 产物 |
|------|------|------|
| 系统级：新系统 / 跨模块重构 / 数据库选型 | → A. 架构设计 | `docs/project/architecture.md` |
| 功能级：单功能 / 接口 / 字段变更 | → B. 功能设计 | `docs/features/{name}/design.md` |

## 硬门

**方案未被用户批准前，不写任何代码、不创建文件结构外的实现。** 无论方案多简单。

## 前置

- 先确认有需求文档（`requirements-*.md` 或 `docs/specs/*-design.md`）；没有就先走 `/requirements`。
- 不擅改需求文档。发现需求边界不对 → 提阻塞项，回 `/requirements` 改，不在方案里悄悄改需求。

## 方案状态流转

- `draft_`：方案未定，和用户讨论迭代
- `ready_`：用户批准，交给 `/arch-review` 评审或 `/dev-workflow` 开发
- `done`：开发完成后归档

## 共同流程

1. **Phase 0 代码探索** — 确认涉及到的 API/组件/表真实存在（遵循 [`rules/tools/code-access.md`](../../rules/tools/code-access.md)：先索引、后 Read）。方案对不上代码是最常见的失败。
2. **方案选型** — 给 1-2 个备选 + 你的推荐，讲清权衡。禁止"都可以"。
3. **影响半径** — 这次改动牵动哪些模块/接口/数据库/前端，逐个列出。
4. **变更清单** — 协议字段、代码层、数据库变更，逐项可溯源到代码落点。
5. **验证手段** — 每个变更点怎么证明做对了：单测 / 接口测试 / 手工步骤。产生方案的人同时给出验证手段。
6. **风险与可逆性** — 最坏情况是什么，能否回退。

## 语义二分（联想用于搜索，引用用于决策）

- 找落点（影响半径、代码位置）：允许大胆联想关键词/相近命名，加速定位
- 定决策（变更清单、交互行为）：必须有需求文档/设计稿/用户原话作依据，禁止"看起来像同类就加"

## 认知模式（复用 `/arch-review`）

- 爆炸半径：出问题影响多大？
- 无聊优先：成熟可预测，不追新
- 增量优于革命：渐进改造，不推倒重来
- 可逆性：优先选容易回退的方案
- 两周检验：两周后回头看还合理吗？

## 完成标准

- [ ] 方案已对照需求文档每条验收标准
- [ ] 影响半径明确（每个改动点可溯源到代码落点）
- [ ] 每个变更点都有验证手段
- [ ] 方案保存到对应产物路径
- [ ] 用户明确批准方案（"可以" / "就这样" / "开始"）

## 反模式

❌ 方案没批准就写代码
❌ 需求边界没确认就设计（回 `/requirements`）
❌ 悄悄改需求文档 / 超出需求范围加设计
❌ 方案落到代码里找不到落点（影响半径不清）
❌ 只给方案不给验证手段
❌ 让"历史问题/以后再说"糊弄掉风险
