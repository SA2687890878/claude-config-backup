# 并行审查(已内化 → 见 review)

> **已内化：本策略已并入 `review` 按规模自动调度，不直接对外触发。** 对外说"审查"请走 `/review`。
> 原适用:较大变更(>100 行 / 跨模块 / 涉及数据流或接口改动)，现由 `review` 自动判断（0-50 单代理/50-200×1对抗/>200×2对抗+四维度并行）。

## 流程

### 1. 收集变更上下文
- `git diff` 摘要 + 变更文件清单(路径、行数)
- 关联材料:需求/设计文档、Task Contract(如有)

### 2. 并行派发(3-4 个子代理,同一批发起)
每个子代理只读审查,专注一个维度,输出统一格式:

| 维度 | 关注点 |
|------|--------|
| 架构/设计 | 模块边界、耦合、可扩展性、是否偏离方案、命名与结构一致性 |
| 安全 | 注入、硬编码密钥、权限校验、输入校验、敏感数据泄露 |
| 性能 | 热点循环、N+1 SQL、缓存缺失、异步阻塞(.Result/.Wait)、大对象 |
| 正确性+边界 | 逻辑错误、空值/并发/异常路径、向后兼容、错误处理、资源释放 |

每个子代理输出:
```markdown
## 审查报告:<维度>
### 问题清单
- [P0|P1|P2|P3] 问题描述 → 证据(文件:行号)→ 建议
### 亮点
(可选的做得好的地方)
```

### 3. 汇总
- 冲突点:各维度意见矛盾的地方(重点核查)
- 风险排序:按严重度 P0 > P1 > P2 汇总
- 结论:通过 / 需修改(列出必须修项)

### 4. 输出与跟进
- 统一报告给用户;P0/P1 项列入修复待办
- 修复后小步重验,再走 `verification-before-completion`

## 约定
- 子代理**只读**,禁止改代码(修复由主会话执行)
- 严重度:P0 阻断 / P1 必须修 / P2 建议 / P3 可选
- 审查依据:`harness-rules` 质量门 + `knowledge/rules/quality/review-checklist.md`
- 加密项目:子代理同样遵守 code-access(索引定位,不直接 Read 整个文件)
