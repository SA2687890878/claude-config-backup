# 快速审查详细流程

## 适用场景

- 只改了几行代码（< 50 行 diff）
- 非关键路径的小改动
- 用户说"快速看看"、"quick review"、"这几行有问题吗"
- 提交前的快速自检

## 格式

```
L<行号>: <严重级别标签>: <问题>. <修复>.
```

跨文件时：
```
<文件>:L<行号>: <严重级别标签>: <问题>. <修复>.
```

## 严重级别标签

| 标签 | 含义 | 处理 |
|------|------|------|
| `🔴 bug:` | 破坏性行为，会导致事故 | 必须修复 |
| `🟡 risk:` | 能跑但脆弱（竞态、null、吞异常） | 强烈建议修复 |
| `🔵 nit:` | 风格、命名、微优化 | 可忽略 |
| `❓ q:` | 真正的问题，不是建议 | 需要回答 |

## 规则

**必须包含：**
- 精确行号
- 精确符号名（用反引号包裹）
- 具体修复方案，不是"考虑重构"

**禁止：**
- 客套话（"我注意到..."、"看起来..."、"你可能想..."）
- 复述代码做了什么（审查者能看 diff）
- 猜测（不确定就用 `❓ q:`）
- 每条都加"写得不错！"（最多在开头说一次）

**自动切换回完整模式：**
- 安全漏洞（CVE 级别）→ 需要完整解释 + 引用
- 架构分歧 → 需要论证，不是一行能说清
- 作者是新人 → 需要解释"为什么"

## 示例

**❌ 差的审查：**
```
我注意到第 42 行你在访问 email 属性之前没有检查 user 对象是否为 null。
如果数据库中找不到用户，这可能会导致崩溃。你可能想在这里添加一个 null 检查。
```

**✅ 好的审查：**
```
L42: 🔴 bug: .find() 后 user 可能为 null。在 .email 前加守卫。
```

**❌ 差的审查：**
```
看起来这个函数做的事情太多了，可能值得拆分成更小的函数来提高可读性。
```

**✅ 好的审查：**
```
L88-140: 🔵 nit: 50 行函数做了 4 件事。拆分为 validate/normalize/persist。
```

**❌ 差的审查：**
```
你有没有考虑过如果 API 返回 429 会怎样？我觉得我们应该处理这种情况。
```

**✅ 好的审查：**
```
L23: 🟡 risk: 429 未重试。用 withBackoff(3) 包装。
```

## 与完整审查的关系

快速审查是完整审查的**轻量替代**，不是替代品。以下情况应切换到完整审查（分支 A）：
- 变更超过 50 行
- 涉及安全、认证、数据迁移
- 跨层变更（Controller → Service → DB）
- 用户要求完整审查
