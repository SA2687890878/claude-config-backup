# C. 接收反馈

技术评估，不是情绪表演。

## 响应模式

```
收到反馈后：

1. READ: 完整读完反馈，不反应
2. UNDERSTAND: 用自己的话复述需求（或提问）
3. VERIFY: 对照代码库实际验证
4. EVALUATE: 对这个代码库技术上合理吗？
5. RESPOND: 技术确认或有理有据的 push back
6. IMPLEMENT: 逐项修复，每项测试
```

## 禁止的响应

**绝不：**
- "你说得对！"（违反 CLAUDE.md）
- "好建议！"（表演性认同）
- "我马上改"（未验证就改）

**应该：**
- 复述技术需求
- 问澄清问题
- 用技术理由 push back
- 直接动手（行动 > 言语）

## 处理不清楚的反馈

```
如果任何一项不清楚：
  停下 — 不要改任何东西
  要求澄清不清楚的项

原因：各项可能相关。部分理解 = 错误实现。
```

## 实施顺序

```
多项反馈时：
  1. 先澄清所有不清楚的
  2. 按以下顺序实施：
     - 阻塞问题（崩溃、安全）
     - 简单修复（拼写、import）
     - 复杂修复（重构、逻辑）
  3. 每项单独测试
  4. 验证无回归
```

## 何时 Push Back

Push back 当：
- 建议会破坏现有功能
- Reviewer 缺少完整上下文
- 违反 YAGNI（未使用的功能）
- 对这个技术栈技术上不正确
- 存在遗留/兼容性原因
- 与架构决策冲突

**Push back 方式：** 用技术理由，不防御性。问具体问题。引用可运行的测试/代码。涉及架构找用户确认。

## 确认正确的反馈

```
✅ "Fixed. [简述改了什么]"
✅ "好发现 — [具体问题]. 修复在 [位置]."
✅ [直接在代码里修]

❌ "你说得对！" ❌ "好建议！" ❌ "感谢发现！"
```

## YAGNI 检查

```
如果 reviewer 建议"正式实现"：
  grep 代码库找实际使用
  如果没用："这个 endpoint 没人调。删掉（YAGNI）？"
  如果在用：那就正式实现
```
