# 代码审查

## 核心原则

**用户说"审查"，agent 自动决定策略。**

不需要用户选择"快速"还是"深度"，不需要用户指定"人工"还是"自动"。

## 策略树

```
用户说"审查"
    │
    ▼
┌─────────────────────────────────────────┐
│ 第一步：收集变更                          │
│ git diff --name-only HEAD               │
└─────────────────────────────────────────┘
    │
    ▼
┌─────────────────────────────────────────┐
│ 第二步：自动分析                          │
│ - 变更规模（行数）                        │
│ - 变更类型（文件扩展名）                   │
│ - 安全敏感度                              │
└─────────────────────────────────────────┘
    │
    ├─ 变更 < 50 行 ──────────────────────→ 快速审查
    │
    ├─ 变更 50-200 行 ────────────────────→ 标准审查
    │
    ├─ 变更 > 200 行 ────────────────────→ 深度审查
    │
    ├─ 涉及 auth/crypto/database ─────────→ 安全审查
    │
    └─ 涉及 test 文件 ───────────────────→ 测试审查
    │
    ▼
┌─────────────────────────────────────────┐
│ 第三步：执行审查                          │
│ 根据策略读取对应的 reference              │
└─────────────────────────────────────────┘
    │
    ▼
┌─────────────────────────────────────────┐
│ 第四步：输出报告                          │
│ 严重程度 + 问题 + 修复建议                │
└─────────────────────────────────────────┘
```

## 审查策略详情

### 策略 1：快速审查

**触发条件：** 变更 < 50 行

**读取：** `references/quick-review.md`

**输出格式：**
```
L42: 🔴 bug: null 检查缺失，.find() 后可能为 null。加守卫。
L88: 🔵 nit: 50 行函数做了 4 件事。拆分为 validate/normalize/persist。
```

### 策略 2：标准审查

**触发条件：** 变更 50-200 行

**读取：** `references/checklist.md`

**按文件类型选择审查维度：**

| 文件类型 | 审查重点 | 读取 |
|----------|---------|------|
| `.cs` | 空指针、资源泄露、异步问题、SQL 注入 | `references/dotnet-checklist.md` |
| `.vue` | v-for key、computed 副作用、XSS | `references/vue-checklist.md` |
| `.js` / `.ts` | 类型安全、异步处理、内存泄露 | `references/checklist.md` |
| `.sql` | 注入风险、性能、索引 | `references/sql-checklist.md` |
| `*.json` / `*.xml` | 配置安全、敏感信息泄露 | `references/config-checklist.md` |

### 策略 3：深度审查

**触发条件：** 变更 > 200 行

**读取：** `references/checklist.md` + `references/execute-review.md`

**流程：**
1. 完整 checklist 逐项检查
2. 派独立 agent 审查（读取 `references/adversarial-prompt.md`）
3. 汇总去重
4. 生成完整报告

### 策略 4：安全审查

**触发条件：** 涉及 auth/crypto/database

**读取：** `references/dotnet-checklist.md` + `references/sql-checklist.md`

**重点：**
- SQL 注入风险
- 认证授权逻辑
- 密钥泄露
- 权限校验

### 策略 5：测试审查

**触发条件：** 涉及 test 文件

**读取：** `references/checklist.md`

**重点：**
- 测试覆盖率
- 断言质量
- 测试隔离

## 严重程度定义

- **CRITICAL** — 生产必炸（数据丢失、安全漏洞、死锁）
- **HIGH** — 很可能出问题（未处理异常、资源泄漏）
- **MEDIUM** — 可能出问题（边界条件、性能隐患）
- **LOW** — 代码质量（命名、冗余、可读性）

## 输出报告格式

```
## 审查报告

### 变更概览
- 文件数：X 个
- 变更行数：X 行
- 审查策略：快速/标准/深度/安全/测试

### 发现
| 严重程度 | 文件:行号 | 问题 | 修复建议 |
|---------|----------|------|---------|
| CRITICAL | ... | ... | ... |

### 统计
- CRITICAL: X 个
- HIGH: X 个
- MEDIUM: X 个
- LOW: X 个

### 建议
- 必须修复：[CRITICAL + HIGH]
- 建议修复：[MEDIUM]
```

## 审查原则

### 必须做的

1. **每个文件都要审查** — 不跳过任何文件
2. **每个问题都要定位** — 给出具体行号
3. **每个问题都要修复建议** — 不只是指出问题
4. **默认质疑** — 除非代码确实无问题
5. **按策略审查** — 不同文件类型用不同清单

### 禁止做的

1. **禁止说"代码看起来不错"** — 除非真的无问题
2. **禁止只说"可以优化"** — 要给出具体优化方案
3. **禁止遗漏 CRITICAL 问题** — 这是不可接受的
4. **禁止主观偏好** — 只报告真实问题
