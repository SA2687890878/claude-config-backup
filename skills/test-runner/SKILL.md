# 测试执行闭环

## 核心铁律

**测试没跑完，不许说"应该通过"。** 必须看到实际输出。

## 路由

| 意图 | 分支 |
|------|------|
| 运行测试看结果（"跑测试"、"测试过了吗"） | → A. 运行测试 |
| 测试失败要修复（"测试失败了"、"修复测试"） | → B. 失败修复循环 |
| 回归测试（"回归"、"确认没坏"） | → C. 回归验证 |
| 不确定 | → A. 运行测试（默认） |

---

## A. 运行测试

### Step 1: 执行

```bash
dotnet test --no-restore --verbosity normal
```

### Step 2: 解析结果

读取输出，提取：
- 总测试数、通过数、失败数、跳过数
- 失败测试的名称和错误信息
- 失败的文件和行号

### Step 3: 报告

```markdown
## 测试结果

| 指标 | 数值 |
|------|------|
| 总数 | N |
| 通过 | N |
| 失败 | N |
| 跳过 | N |

### 失败详情
- `TestName` — `文件:行号` — 错误信息
```

**全部通过** → 报告成功。
**有失败** → 问用户是否进入修复循环。

---

## B. 失败修复循环

读取 `references/failure-patterns.md` 了解常见失败模式和修复策略。

### 循环流程

```
while 有失败的测试:
    1. 选一个失败测试（优先 CRITICAL/HIGH）
    2. 定位失败位置（文件:行号）
    3. 分析根因（读代码 + 读错误信息）
    4. 最小化修复（只改必须改的）
    5. 单独运行这个测试确认通过
    6. 运行全部测试确认无回归
```

### 退出条件

- 全部通过 → 报告成功
- 连续 3 次修复同一个测试仍失败 → 停下，报告问题，请求用户介入
- 修复引入新的失败 → 停下，报告冲突

### 修复原则

- 先理解为什么失败，再动手修
- 只修根因，不改测试来"凑绿"
- 每次只改一个地方
- 修完立即验证

---

## C. 回归验证

在功能开发或 bug 修复后，运行完整测试套件确认没有引入回归。

```bash
dotnet test --no-restore --verbosity normal
```

全部通过 → 回归验证通过。
有失败 → 进入 B. 失败修复循环。
