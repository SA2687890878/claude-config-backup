# 系统化调试

## 核心铁律

**没有根因调查，不允许修复。** 随机修复浪费时间、引入新 bug。

> **代码探索铁律**：定位 bug 时先用索引追调用链、最后才 Read。遵循 [`rules/tools/code-access.md`](../../rules/tools/code-access.md)：search.ps1 -Callers/-Callees 是调试追踪首选。

## 五个阶段

每个阶段必须完成才能进入下一个。

**Phase 0: 建反馈循环** — 先建一个能稳定复现问题的命令
**Phase 1: 根因调查** — 读错误、复现、检查变更、收集证据
**Phase 2: 模式分析** — 找可工作示例、对比差异
**Phase 3: 假设与测试** — 形成理论、最小化测试
**Phase 4: 实现修复** — 创建测试、修复、验证

**3+ 次修复失败 = 架构问题。** 停下，质疑架构，和用户讨论。

---

## Phase 0: 建反馈循环

**在猜原因之前，先建一个能稳定复现问题的命令。** 这是整个调试过程中最重要的阶段。

### .NET 场景建循环方式（按优先级）

1. **失败的测试** — 在 bug 相关的 seam 写一个 failing test（首选）
2. **API 调用** — HTTP 文件或 curl 调 dev server
3. **最小化复现** — 写一个控制台程序，只触发 bug 路径
4. **数据库查询** — 验证数据状态是否符合预期
5. **日志注入** — 加 [DEBUG-xxx] 前缀的临时日志
6. **git bisect** — bug 是近期引入时

### 完成标准

运行一条命令，它满足：
- [ ] **红色能力** — 驱动 bug 代码路径并断言用户的精确症状
- [ ] **确定性** — 每次运行结果一致
- [ ] **快速** — 秒级，不是分钟级
- [ ] **Agent 可运行** — 不需要人工在循环中

### 反模式

❌ 如果你发现自己在读代码猜原因 → 停下来 → 先建循环。
❌ 没有 red-capable 的命令，不进入 Phase 1。
❌ 不要"log everything and grep"——只在能区分假设的边界加日志。

---

## Phase 1: 根因调查

收集证据，理解问题的边界。

### 步骤

1. **读错误信息** — 完整读，不要跳过。提取：错误类型、消息、堆栈、行号
2. **复现** — 用 Phase 0 的循环复现。如果不能复现，问用户获取更多信息
3. **检查变更** — `git log --oneline -10` 和 `git diff HEAD~3`。问题通常是最近引入的
4. **收集证据** — 运行诊断命令，记录实际输出

### 完成标准

- [ ] 能用 Phase 0 的循环稳定复现问题
- [ ] 知道问题的边界（什么情况下出、什么情况下不出）
- [ ] 有至少一条具体的错误信息或堆栈

### 反模式

❌ 不要在没有复现的情况下猜测原因。
❌ 不要跳过错误信息直接看代码。

---

## Phase 2: 模式分析

找可工作示例，对比差异。

### 步骤

1. **找类似功能** — 搜索代码库中类似的、正常工作的模块
2. **对比差异** — 逐行对比 working vs broken 的实现
3. **识别模式** — 哪些模式是正确的，哪些是缺失的

### 完成标准

- [ ] 至少找到一个 working 示例
- [ ] 识别出 working 和 broken 之间的具体差异
- [ ] 差异指向一个可能的原因

---

## Phase 3: 假设与测试

形成理论，最小化测试。

### 步骤

1. **生成 3-5 个假设** — 不要只生成 1 个（单一假设 = 锚定效应）
2. **每个假设可证伪** — 说清楚"如果 X 是原因，那么改变 Y 会让 bug 消失"
3. **展示给用户排优先级** — 用户有领域知识，能瞬间重排
4. **逐个测试** — 每次只改一个变量

### 假设格式

| # | 假设 | 可证伪预测 | 优先级 |
|---|------|-----------|--------|
| 1 | [描述] | 如果 [X] 是原因，那么 [Y] 会让 bug 消失 | 高/中/低 |

### 完成标准

- [ ] 至少 3 个假设已列出
- [ ] 每个假设有可证伪的预测
- [ ] 用户已确认优先级（或用户 AFK 时按自己的排序执行）
- [ ] 至少一个假设已测试

### 反模式

❌ 不要只生成 1 个假设就开测——这是锚定效应。
❌ 不要测试不可证伪的假设（"可能是网络问题"不是假设）。

---

## Phase 4: 实现修复

创建测试、修复、验证。

### 步骤

1. **写回归测试** — 在修复之前写。测试应该能复现 bug
2. **确认测试失败** — 运行测试，确认红色
3. **修复** — 最小化修复，不改测试来"凑绿"
4. **确认测试通过** — 运行测试，确认绿色
5. **运行完整测试** — `dotnet test`，确认无回归

### 完成标准

- [ ] 回归测试已写且能复现 bug
- [ ] 修复后测试通过
- [ ] 完整测试套件通过（无回归）
- [ ] Phase 0 的循环也能通过

### 反模式

❌ 不要改测试来"凑绿"——如果测试需要改，先确认是测试错了还是代码错了。
❌ 不要在没有回归测试的情况下修复——bug 会回来。

---

## 调试日志纪律

- 每条 debug log 加唯一前缀：`[DEBUG-a4f2]`
- 修复后 grep 前缀，一次性删除所有调试日志
- 一个断点胜过十条日志（如果有 debugger 可用）

## 安全操作

### 路由

| 意图 | 分支 |
|------|------|
| 破坏性命令防护（执行危险命令前） | → A. 命令防护 |
| 代码修改影响评估（改遗留代码前） | → B. 修改评估 |
| 安全扫描（"扫描"、"漏洞"、"安全检查"） | → C. 安全扫描 |
| 不确定 | → 问用户 |

---

### A. 命令防护

执行危险命令前必须先警告用户并等待确认。

**危险命令模式：**
- Bash: `rm -rf`, `git push --force`, `git reset --hard`
- SQL: `DROP TABLE`, `TRUNCATE`, `DELETE FROM` 无 WHERE
- PS: `Remove-Item -Recurse -Force`

读取 `references/command-guard-details.md` 了解完整列表。

---

### B. 修改评估

遗留代码可以改，但必须评估后改。

**核心原则：**
1. 能新增就不改
2. 必须改就评估
3. 记录改动

读取 `references/modification-assessment-details.md` 了解评估流程。

---

### C. 安全扫描

系统化检测代码中的安全问题。

**扫描范围：**
1. 依赖漏洞
2. 硬编码密钥
3. SQL 注入
4. XSS
5. 认证授权
6. 敏感数据泄露

读取 `references/security-scan-details.md` 了解完整扫描流程。
