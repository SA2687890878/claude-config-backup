# 系统化调试详细流程

## Phase 1: 根因调查

**在尝试任何修复之前：**

1. **仔细读错误信息** — 不要跳过。堆栈跟踪、行号、错误码往往包含答案
2. **稳定复现** — 能可靠触发吗？不能复现 → 收集更多数据，不猜
3. **检查最近变更** — git diff、最近 commit、新依赖、配置变化
4. **多组件系统：加诊断日志** — 在每个组件边界记录输入/输出，定位断点在哪一层
5. **追踪数据流** — 坏值从哪来？谁传进来的？从错误位置往上追到源头

## Phase 2: 模式分析

1. **找可工作的类似代码** — 同代码库里类似的、能正常工作的代码
2. **对比差异** — 逐项列出工作和不工作的区别
3. **读参考实现** — 如果在实现某个模式，完整读完参考实现，不跳读

## Phase 3: 假设与测试

1. **生成 3-5 个假设** — 不要只生成 1 个（单一假设 = 锚定效应）
2. **每个假设可证伪** — "如果 X 是根因，那么改变 Y 会让 bug 消失"
3. **展示给用户排优先级** — 用户有领域知识，能瞬间重排
4. **逐个测试** — 每次只改一个变量
5. **验证后再继续** — 没效果？测下一个假设，不要叠加更多修复

## Phase 4: 实现修复

1. **创建失败测试** — 最简单的复现，自动化测试优先
2. **实现单一修复** — 只修根因，不做"顺便"改进
3. **验证修复** — 测试通过？其他测试没坏？问题真正解决？

**3+ 次修复失败 = 架构问题。** 停下，质疑架构，和用户讨论。

## 红旗 — 停下返回 Phase 1

如果你在想：
- "先快速修一下，以后再查"
- "试试改 X 看看"
- "我大概理解了，试试这个"
- "修了好几次了，再试一次"（3+ 次 = 架构问题）
- 每次修都暴露新的不同位置的问题

**所有这些 = 停下，返回 Phase 1。**

## 快速参考

| 阶段 | 关键活动 | 成功标准 |
|------|---------|---------|
| 1. 根因 | 读错误、复现、检查变更、收集证据 | 理解 WHAT 和 WHY |
| 2. 模式 | 找可工作示例、对比差异 | 识别不同点 |
| 3. 假设 | 生成 3-5 个假设、可证伪预测、用户排优先级、逐个测试 | 至少一个假设已验证 |
| 4. 实现 | 创建测试、修复、验证 | Bug 解决、测试通过 |
