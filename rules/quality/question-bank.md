# 需求澄清问题库

> 按工作阶段分类的高信号问题。用于需求不明确时快速澄清。
> 借鉴自 COMPASS Skills 的 question-bank 设计，适配你的日常工作场景。

## 使用规则

- **每轮最多问 1 个问题**，带推荐答案
- 用户决策优先于外部研究
- 高风险操作（删除、发布、数据库变更）必须确认
- 如果用户说"直接做"/"不用问"，跳过澄清循环（高风险操作仍需确认）

## 什么时候需要澄清

需求包含以下信号时，必须澄清：
- 模糊词："优化"/"改进"/"最好"/"合适"
- 范围不明：没说改哪个模块/文件/接口
- 验收不明：没说什么算"完成"
- 约束不明：有硬限制但没说（预算、时间、兼容性）

不需要澄清的情况：
- 明确的 typo 修复（文件+行号+内容都指定了）
- 纯事实查询
- 用户已明确说了"直接做"

## 1. 需求沟通阶段

### 核心三问（必须回答）

**Outcome — 你想要什么结果？**
> 修复 bug / 新增功能 / 重构 / 性能优化 / 文档？
> 我的建议：看上下文推断，但必须确认。

**Constraints — 有什么硬限制？**
> 时间 / 预算 / 框架版本 / 兼容性 / 数据库？
> 我的建议：从项目上下文推断技术限制，但业务限制必须问。

**Acceptance — 怎么算成功？**
> 测试通过 / 功能正常 / 性能达标 / 审查通过？
> 我的建议：至少测试通过 + 功能正常。

### 高信号问题

**Scope — 改动范围？**
> 最小修复 / 干净重构 / 深度优化？
> 我的建议：最小修复，除非用户明确要求重构。

**Risk — 风险边界？**
> 可以改数据库结构吗？可以改公共 API 吗？
> 我的建议：不改公共 API，不改数据库结构，除非用户确认。

---

## 2. 架构设计阶段

**Scale — 规模预期？**
> 用户量 / QPS / 数据量 / 团队规模？
> 我的建议：先问，因为规模决定技术选型。

**Tradeoffs — 优先级？**
> 一致性 vs 可用性 / 速度 vs 正确性 / 简单 vs 灵活？
> 我的建议：先简单，后优化，保持可变性。

**Migration — 现有系统？**
> 全新开发 / 集成现有 / 替换现有？
> 我的建议：默认集成现有，除非用户说全新。

**Team — 团队熟悉度？**
> 用团队熟悉的技术，还是引入新技术？
> 我的建议：优先用已有的技术栈。

---

## 3. 功能设计阶段

**Deliverable — 交付物形式？**
> 代码 PR / 设计文档 / 原型 / 生产就绪？
> 我的建议：代码 PR + 简要说明。

**Audience — 给谁看？**
> 自己 / 同事 / 领导 / 客户？
> 我的建议：默认给开发者看。

**Evidence — 证据标准？**
> 必须有测试 / 有文档就行 / 能跑就行？
> 我的建议：至少有测试。

---

## 4. 功能开发阶段

**Test scope — 测试要求？**
> 现有测试通过 / 新增测试 / 手动验证？
> 我的建议：现有测试通过 + 新增测试覆盖改动。

**Rollback — 回滚策略？**
> git revert / feature flag / 手动回滚？
> 我的建议：git revert，保持可回滚。

**Dependencies — 依赖变更？**
> 可以升级依赖吗？可以加新依赖吗？
> 我的建议：不加新依赖，除非必要。

---

## 5. 问题排查阶段

**Reproduction — 复现步骤？**
> 能描述复现步骤或提供错误输出吗？
> 我的建议：必须能复现才能修。

**Environment — 环境信息？**
> 什么 OS / 运行时版本 / 本地还是 CI 还是生产？
> 我的建议：先问，因为环境影响排查方向。

**Recent changes — 最近变更？**
> 出问题前改了什么？部署 / 依赖更新 / 配置变更？
> 我的建议：查 git log。

**Urgency — 紧急程度？**
> 现在阻塞吗？可以慢慢修吗？
> 我的建议：先定位根因，再决定修法。

---

## 6. 推荐/选择场景

**Use case — 使用场景？**
> 日常使用 / 专业场景 / 特殊需求？
> 我的建议：问用户，不要假设。

**Budget — 预算？**
> 免费 / 有限预算 / 不限？
> 我的建议：必须问，没有安全默认值。

**Ranking — 优先级？**
> 价格 / 耐用 / 功能 / 品牌，哪个优先？
> 我的建议：可靠性 > 易用性 > 价格。

**Output — 输出形式？**
> 单个推荐 / 短名单 / 详细对比？
> 我的建议：单个推荐 + 2 个备选 + 权衡说明。

## 快速参考

### 问题选择原则

1. **上游优先**：Outcome 不清楚时，不要问 Scope
2. **影响最大优先**：选那个答案最影响执行路径的问题
3. **独立性**：如果两个问题答案互相影响，分开问

### 推荐答案格式

```
我需要确认 [具体变量]，因为 [它如何影响结果]。
我的建议：[推荐答案]。
你也可以选：[2-4 个选项] / 或者告诉我你的想法。
```

### 确认格式

```
我理解你需要：[2-5 行总结]
我假设：[列出假设，特别是从上下文推断的]
这样理解对吗？有没有我漏掉的？
```
