# Quality Gate 体系

> 所有工作流必须通过对应的质量门禁。门禁是强制的，不可跳过。

## 门禁概览

| 门禁 | 时机 | 检查内容 | 通过条件 |
|------|------|---------|---------|
| Requirement Gate | 需求探索完成后 | 需求完整性、可测试性 | 所有检查项通过 |
| Design Gate | 设计完成后 | 设计合理性、可扩展性 | 所有检查项通过 |
| Code Gate | 编码完成后 | 代码质量、安全性 | 编译通过 + 审查通过 |
| Test Gate | 测试完成后 | 测试覆盖率、回归 | 所有测试通过 |
| Release Gate | 发布前 | 风险评估、回滚方案 | 所有检查项通过 |

---

## 1. Requirement Gate

**时机**：需求探索完成后，进入设计阶段前

### 检查项

#### 完整性
- [ ] 功能需求是否明确（不是"用户觉得..."）
- [ ] 验收标准是否可衡量（Given/When/Then）
- [ ] 边界条件是否定义（正常/异常/边界值）
- [ ] 约束条件是否列出（技术/业务/时间）

#### 无歧义
- [ ] 术语是否统一（同一概念只用一个词）
- [ ] 需求是否可测试（能写测试用例验证）
- [ ] 需求是否可实现（技术上可行）

#### 可验收
- [ ] 验收标准是否具体（不是"用户体验好"）
- [ ] 验收标准是否可自动化（能用代码验证）
- [ ] 验收标准是否完整（覆盖所有功能点）

### 通过条件
- 所有检查项都通过
- 用户确认需求文档

### 失败处理
- 返回需求探索阶段补充信息
- 记录缺失项，要求用户补充

---

## 2. Design Gate

**时机**：设计完成后，进入编码阶段前

### 检查项

#### 满足需求
- [ ] 设计是否覆盖所有功能需求
- [ ] 设计是否满足非功能需求（性能/安全/可用性）
- [ ] 设计是否符合约束条件

#### 可扩展性
- [ ] 模块划分是否合理（单一职责）
- [ ] 依赖方向是否正确（高层不依赖低层）
- [ ] 接口设计是否稳定（不易频繁变更）

#### 性能风险
- [ ] 是否有 N+1 查询风险
- [ ] 是否有大数据量处理
- [ ] 是否有并发安全问题

#### 数据风险
- [ ] 数据库设计是否符合范式
- [ ] 索引设计是否合理
- [ ] 数据迁移方案是否可行

### 通过条件
- 所有检查项都通过
- 架构审查通过（无 CRITICAL/HIGH 问题）

### 失败处理
- 返回设计阶段修改
- 记录问题，要求设计者修复

---

## 3. Code Gate

**时机**：编码完成后，进入测试阶段前

### 检查项

#### 编译通过
- [ ] `dotnet build --configuration Release` 退出码 == 0
- [ ] 无编译错误
- [ ] 无编译警告（可选，视项目配置）

#### 代码审查通过
- [ ] 无 CRITICAL 问题
- [ ] 无 HIGH 问题（或已标记为可接受）
- [ ] MEDIUM 问题已评估风险

#### 代码质量
- [ ] 命名符合项目规范
- [ ] 方法长度合理（<50 行）
- [ ] 无重复代码
- [ ] 异常处理完善

#### 安全性
- [ ] 无 SQL 注入风险
- [ ] 无 XSS 漏洞
- [ ] 无硬编码密钥
- [ ] 权限校验正确

### 通过条件
- 编译通过
- 代码审查通过（无 CRITICAL/HIGH）
- 安全扫描通过

### 失败处理
- 返回编码阶段修复
- 记录问题，要求开发者修复

---

## 4. Test Gate

**时机**：测试完成后，进入发布阶段前

### 检查项

#### 测试通过
- [ ] `dotnet test` 退出码 == 0
- [ ] 所有测试通过（0 失败）
- [ ] 无跳过的测试（或已说明原因）

#### 覆盖率
- [ ] 主流程测试覆盖
- [ ] 异常流程测试覆盖
- [ ] 边界条件测试覆盖

#### 回归
- [ ] 现有测试无回归
- [ ] 新增功能有对应测试
- [ ] 修复的 bug 有复现测试

### 通过条件
- 所有测试通过
- 覆盖率达标（视项目要求）
- 无回归

### 失败处理
- 返回测试阶段补充测试
- 记录失败测试，要求修复

---

## 5. Release Gate

**时机**：发布前，部署到生产环境前

### 检查项

#### 风险评估
- [ ] 变更范围评估（影响哪些模块）
- [ ] 数据风险评估（是否有数据迁移）
- [ ] 性能风险评估（是否有性能影响）
- [ ] 安全风险评估（是否有安全漏洞）

#### 回滚方案
- [ ] 回滚步骤是否明确
- [ ] 回滚时间是否可接受
- [ ] 数据回滚是否可行

#### 发布方案
- [ ] 发布步骤是否明确
- [ ] 发布时间是否合适（避开高峰期）
- [ ] 监控方案是否就绪

#### 文档
- [ ] 变更日志是否更新
- [ ] API 文档是否更新（如有接口变更）
- [ ] 用户文档是否更新（如有功能变更）

### 通过条件
- 所有检查项都通过
- 用户确认发布

### 失败处理
- 返回对应阶段修复
- 记录风险，要求制定缓解措施

---

## 门禁执行规则

### 强制性
- 门禁是强制的，不可跳过
- 任何门禁失败都必须修复后重新验证
- 不允许"先发布再修复"

### 证据要求
- 每个门禁必须有实际运行的命令和输出
- 不能声称通过但没有实际验证
- 退出码是唯一的判定标准

### 记录要求
- 门禁结果必须记录
- 失败原因必须记录
- 修复措施必须记录

---

## 门禁集成

### 工作流集成

每个工作流必须在对应阶段执行门禁检查：

- **explore** → Requirement Gate
- **build** → Design Gate → Code Gate → Test Gate
- **operate** → Code Gate → Test Gate

### Hook 集成

- `build-verify.js` — 会话结束时自动执行 Code Gate
- `quality-guard.js` — 代码修改时自动检查质量

### 输出格式

```
## 门禁检查：[门禁名称]

### 检查项
- [x] 检查项 1 — 通过
- [x] 检查项 2 — 通过
- [ ] 检查项 3 — 失败：[原因]

### 结果
PASS / FAIL

### 证据
- 命令：[实际运行的命令]
- 输出：[实际返回的内容]

### 失败处理
- [如果失败，记录修复措施]
```
