# 需求评审方法论

> 提炼自 PCS 需求规划 Agent（马诺整理，已去业务化），按需加载。
> 触发词：需求评审 / 需求梳理 / 需求讨论 / 方案取舍 / 影响分析 / 验收条件。
> 配合：`/requirements` skill（流程）+ `gates/requirement.md`（门禁检查）+ `question-bank.md`（澄清问题）。

## 四类信息分类法（评审第一动作）
把评审中获得的信息强制归入四类，绝不混淆：

| 类别 | 定义 | 处理 |
|------|------|------|
| **已确认事实** | 来自代码 / 文档 / 用户明确陈述 | 直接采用，作为方案依据 |
| **合理假设** | 可从上下文合理推断 | 显式标注"假设"，**不得升级为事实** |
| **待确认项** | 影响方案的关键未知 | 必须询问，未确认前方案不标 ready |
| **风险** | 可能改变方案的隐患 | 列出并给缓解方式，写进方案 |

> 失败对照：把"假设"当"事实"是需求评审最常见的幻觉源——方案看起来成立，落地才发现口径错。

## 影响分析清单（六面逐项查）
- 前端（页面 / 组件 / 交互）
- 后端（接口 / 服务 / 鉴权）
- 数据库（表结构 / 索引 / 迁移）
- 菜单权限（路由 / 按钮级权限 / 组织隔离）
- AI 能力（如有：模型协议 / 提示词 / 追踪）
- 外部依赖（第三方服务 / 跨系统协议）

每面明确：数据来源、数据口径、状态流转、异常处理、权限边界、兼容性。

## 方案取舍与可执行验收
- 输出：推荐方案 + 必要备选 + 取舍理由。
- 验收条件必须**可执行**——能写出具体验证动作的才算数（"功能正常"不算，"执行 X 后查询 Y 返回 Z"才算）。
- 需求不明确 / 多方案 / 验收不完整 → 不直接进设计，先评审确认。

## 输出
- 评审摘要：已确认事实 / 假设 / 待确认项 / 风险 / 推荐方案 / 验收条件。
- 只评审不实现；用户确认前不创建规划文件（任务持久化走 `active.json`，见 task-management.md）。
