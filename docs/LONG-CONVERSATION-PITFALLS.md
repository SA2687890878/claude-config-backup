# Harness Engineering: 长对话陷阱

> 上下文过长导致的常见问题和解决方案

**版本**：v1.0.0 | **最后更新**：2026-06-15

---

## 问题现象

### 1. 丢失状态跟踪

**症状**：忘记之前读过什么文件、哪些操作已执行

**例子**：
```
Claude：已读取 UserService.cs
[100 条消息后]
用户：帮我看一下 UserService.cs
Claude：[再次读取 UserService.cs，浪费一次 Read 调用]
```

### 2. 重复执行相同操作

**症状**：重复读取/创建相同文件、执行相同命令

**例子**：
```
Claude：运行命令 dotnet build
[200 条消息后]
Claude：再次运行 dotnet build
[检查上下文中的返回结果]
→ 发现返回内容相同，说明就是重复执行
```

### 3. 死循环

**症状**：操作失败时重复尝试相同操作，没有改变策略

**例子**：
```
Claude：运行 dotnet build
        → 错误：编译失败
Claude：再次运行 dotnet build
        → 错误：同样的编译错误
Claude：再次运行 dotnet build
        → 错误：还是同样的错误
[无限循环，需要 debug 而不是重复执行]
```

---

## 根本原因

1. **上下文窗口接近限制**
   - 模型输出越来越短
   - 推理速度变慢
   - 内存消耗高

2. **没有检查返回结果**
   - 对每个操作的结果没有记录
   - 不知道是否已执行过

3. **没有显式跟踪进度**
   - 没有用 task list 记录已完成的步骤
   - 容易遗忘和重复

---

## 解决方案

### 方案 1：每次操作后检查返回结果

**规则**：检查工具的返回内容，判断是否真的执行了

```
Read 工具返回 "Wasted call — file unchanged"
  → 文件已在上下文中
  → 不要重复读，用之前读过的内容

Bash 工具返回同样的错误信息
  → 相同的命令行为没有改变
  → 改变策略，不要重复执行

Edit 工具返回 "File unchanged"
  → 替换文本没有找到或无改变
  → 检查 old_string 是否正确
```

### 方案 2：用 Task List 跟踪进度

```
你：帮我重构这个模块

Claude：[使用 TaskCreate]
  - [ ] 读取现有模块结构
  - [ ] 设计新架构
  - [ ] 编写新代码
  - [ ] 运行测试
  - [ ] 代码审查

[每完成一步，TaskUpdate 标记为完成]

好处：
  ✅ 避免忘记已执行的操作
  ✅ 新上下文也能看到进度
  ✅ 对话被中断可以恢复
```

### 方案 3：定期压缩对话

**时机**：当感觉响应变慢时

```bash
# 用户在 Claude Code 中执行
/compact

Claude：
  [保留关键决策、已完成的文件、当前进度]
  [移除详细的中间过程]
  [压缩后剩余有效上下文 ~2000 tokens]

好处：
  ✅ 清理冗余信息
  ✅ 恢复推理速度
  ✅ 继续工作
```

### 方案 4：主动结束对话

**信号**：
- 响应时间超过 10 秒
- 输出变得很短（<100 字）
- 用户多次提醒"太慢了"

**处理**：
```
Claude：
检测到上下文已接近限制。
建议结束本轮对话：
  1. 当前进度：已完成功能 A、功能 B
  2. 下一步：功能 C（见 docs/NEXT-STEPS.md）
  3. 恢复方式：新会话中说"继续功能 C"

原因：
  - 长对话会导致资源浪费
  - 新会话会重新加载上下文，更清爽
  - 效率更高
```

---

## 长对话中的最佳实践

### ✅ DO

1. **主动检查返回结果**
   - 每个 Read/Edit/Bash 后看一遍返回内容
   - "文件未改变" → 停止重复操作
   - 错误信息 → 分析原因，改变策略

2. **用 Task List 记录进度**
   - `TaskCreate` 创建任务
   - `TaskUpdate` 标记完成
   - 长对话中自动保存进度

3. **定期检查上下文大小**
   - 观察输出延迟
   - 输出变短 → 上下文接近满
   - 主动建议压缩或结束

4. **记录关键决策**
   ```
   已决定用 Repository 模式而不是 EF Direct
   已决定用 JWT 而不是 Session
   已决定用 async/await 而不是 .Result/.Wait()
   ```

5. **保存中间产物**
   - 设计文档
   - 当前进度
   - 下一步计划
   - 便于新会话继续

### ❌ DON'T

1. **不要盲目重复操作**
   - 看返回结果，确认确实需要重复
   - 否则就是浪费 Token

2. **不要忽视错误信息**
   - 错误通常需要改变策略
   - 重复执行相同操作 = 死循环

3. **不要在一个对话里做太多事**
   - 超过 500 条消息 → 考虑结束
   - 超过 300k tokens → 一定结束
   - 分阶段工作效率更高

4. **不要让对话"糊"起来**
   - 定期总结进度
   - 定期记录决策
   - 不要让用户不知道现在做到哪了

5. **不要硬撑**
   - 响应变慢 → 建议压缩/结束
   - 不要等到完全卡住

## 实际案例

### 案例 1：死循环（重复编译）

**场景**：修复编译错误时

**不良操作**：
```
用户：这个编译错误怎么修？

Claude：运行 dotnet build
        → 错误：找不到类型 'UserService'

Claude：再次运行 dotnet build
        → 错误：找不到类型 'UserService'

Claude：再次运行 dotnet build
        → 错误：找不到类型 'UserService'

Claude：再次运行 dotnet build
        → [已执行 4 次相同命令，0 次分析错误原因]

问题：应该分析错误信息，找到缺少的 using 或引用
```

**良好操作**：
```
用户：这个编译错误怎么修？

Claude：运行 dotnet build
        → 错误：找不到类型 'UserService'

Claude：分析错误信息
        → 根本原因：缺少 using Project.Services;
        → 修复：添加 using 语句

Claude：再次编译
        → 成功：编译完成
```

### 案例 2：重复读取（浪费 Token）

**场景**：代码审查时

**不良操作**：
```
用户：帮我审查这个模块

Claude：读取 UserService.cs（200 行）
        → 审查并提出建议

[50 条消息后]

用户：再看看 UserService.cs

Claude：再次读取 UserService.cs（200 行）
        → [浪费 200 行 Token，其实已经在上下文中]

问题：应该直接使用之前读过的内容
```

**良好操作**：
```
用户：帮我审查这个模块

Claude：读取 UserService.cs（200 行）
        → 审查并提出建议

[50 条消息后]

用户：再看看 UserService.cs

Claude：检查上下文
        → 发现已读取过
        → 直接基于之前内容继续审查
        → [节省 200 行 Token]
```

### 案例 3：状态丢失（忘记进度）

**场景**：长对话开发功能时

**不良操作**：
```
[会话开始]
用户：开发一个用户导出功能

Claude：[分析需求、设计架构、编码...]
       [已经完成 80%]

[200 条消息后]

用户：继续

Claude：[忘记了之前的进度]
        → 从头开始分析需求
        → [浪费之前的所有工作]

问题：应该用 Task List 保存进度
```

**良好操作**：
```
[会话开始]
用户：开发一个用户导出功能

Claude：[TaskCreate 5 个任务]
  - [x] 分析需求
  - [x] 设计架构
  - [ ] 编写代码（进行中）
  - [ ] 运行测试
  - [ ] 代码审查

[200 条消息后]
Claude：自动保存到 task-state.md

用户：继续

Claude：[新会话]
        → 加载 task-state.md
        → 看到上次在"编写代码"
        → 继续编码
```

### 案例 4：真实项目中的长对话问题

**项目**：电商系统订单模块重构

**问题现象**：
- 对话持续 4 小时
- 500+ 条消息
- Token 消耗 300k+
- Claude 响应变慢（>10 秒）

**根本原因**：
1. 没有保存进度，一直在同一个会话中
2. 重复读取相同的文件（每次读 10 个文件）
3. 没有使用 Task List 跟踪
4. 遇到错误时重复尝试相同操作

**解决过程**：
```
1. 保存当前进度
   /verification-before-completion
   → 保存到 task-state.md

2. 结束当前会话
   → 用户手动结束

3. 启动新会话
   → 自动加载 task-state.md
   → 恢复到上次进度

4. 继续工作
   → 使用 Task List 跟踪
   → 避免重复读取
   → 改变策略而不是重复操作
```

**最终效果**：
- 原计划 4 小时 → 实际 2.5 小时（节省 37%）
- Token 消耗从 300k → 120k（节省 60%）
- 质量更高（有 Task List 跟踪，不遗漏）

## 监控指标

### 识别长对话的信号

| 信号 | 含义 | 行动 |
|------|------|------|
| 输出延迟 > 5 秒 | 上下文开始压力 | 定期压缩 |
| 输出变短（<100 字） | 上下文压力大 | 建议压缩 |
| 重复读取同一文件 | 状态追踪失败 | 检查上次输出 |
| 重复执行相同命令 | 死循环迹象 | 改变策略 |
| 用户说"太慢了" | 用户感受延迟 | 立即结束对话 |

## 总结

### 核心规则

```
长对话 3 大原则：

1. 检查每个操作的返回结果
   → 避免重复操作和死循环

2. 用 Task List 跟踪进度
   → 避免丢失状态

3. 主动结束长对话
   → 避免资源浪费
```

### 何时应用

- **当发现重复操作时** — 立即停止，改变策略
- **当对话超过 300 条消息时** — 定期检查进度
- **当响应变慢时** — 压缩或结束
- **当用户感到不适时** — 主动建议结束
