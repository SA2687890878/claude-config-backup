# Harness Engineering: 长对话陷阱

> 上下文过长导致的常见问题和解决方案。

**版本**：v2.0 | **最后更新**：2026-08-27

---

## 问题现象

1. **丢失状态跟踪**：忘记之前读过什么文件、哪些操作已执行
2. **重复执行相同操作**：重复读取/创建相同文件、执行相同命令
3. **死循环**：操作失败时重复尝试相同操作，没有改变策略

---

## 根本原因

1. **上下文窗口接近限制**：模型输出越来越短、推理变慢、内存消耗高
2. **没有检查返回结果**：对每个操作的结果没有记录，不知道是否已执行过
3. **没有显式跟踪进度**：没有用 task list 记录已完成步骤，容易遗忘和重复

---

## 解决方案

### 方案 1：每次操作后检查返回结果
- Read 返回 "file unchanged" → 文件已在上下文中，不要重复读
- Bash 返回同样的错误 → 相同命令行为没变，改变策略
- Edit 返回 "File unchanged" → 替换文本没找到，检查 old_string

### 方案 2：用 Task List 跟踪进度
- 创建任务、标记完成，避免遗忘，对话中断可恢复

### 方案 3：定期压缩对话
- 响应变慢时 `/compact`，清理冗余信息，恢复推理速度

### 方案 4：主动结束对话
- 信号：响应 > 10 秒、输出 < 100 字、用户多次提醒"太慢"
- 处理：总结进度 → 记录下一步 → 新会话说"继续 X"

---

## 最佳实践

**DO**
- 每个 Read/Edit/Bash 后看一遍返回内容
- 用 Task List 记录进度，长对话中自动保存
- 定期检查上下文大小（输出变短 → 上下文接近满）
- 记录关键决策（如"已决定用 Repository 模式"）
- 保存中间产物（设计文档、当前进度、下一步计划）

**DON'T**
- 不要盲目重复操作——看返回结果确认确实需要重复
- 不要忽视错误信息——错误通常需要改变策略
- 不要在一个对话里做太多事（超过 500 条消息 → 考虑结束）
- 不要硬撑——响应变慢就压缩或结束

---

## 监控信号

| 信号 | 含义 | 行动 |
|------|------|------|
| 输出延迟 > 5 秒 | 上下文开始有压力 | 定期压缩 |
| 输出变短（<100 字） | 上下文压力大 | 建议压缩 |
| 重复读取同一文件 | 状态追踪失败 | 检查上次输出 |
| 重复执行相同命令 | 死循环迹象 | 改变策略 |
| 用户说"太慢了" | 用户感受延迟 | 立即结束对话 |

---

## 总结

```
长对话 3 大原则：
1. 检查每个操作的返回结果 → 避免重复操作和死循环
2. 用 Task List 跟踪进度 → 避免丢失状态
3. 主动结束长对话 → 避免资源浪费
```

**何时应用**：发现重复操作 / 对话超 300 条消息 / 响应变慢 / 用户感到不适。
