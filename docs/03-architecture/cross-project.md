# 跨项目工作流

## 适用场景

- 后端加 API + 前端加页面
- Web 后端 + WPF 桌面端同步修改
- 数据库 + 后端 + 前端联动
- 多个微服务协同变更

**触发词：** `跨项目` / `联动开发` / `前后端一起改` / `全栈开发`

---

## 项目自动识别

通过文件特征识别项目类型，**不写死路径**：

| 特征文件 | 项目类型 | Agent 角色 |
|---------|---------|-----------|
| `*.sln` + `*.csproj` | .NET 后端 | 后端实现者 |
| `package.json` + `vue.config.js` | Vue 前端 | 前端实现者 |
| `package.json` + `next.config.js` | Next.js | 前端实现者 |
| `*.csproj` + `App.xaml` | WPF 桌面端 | WPF 实现者 |
| `*.csproj` + `Program.cs` (无 App.xaml) | 控制台/服务 | 服务实现者 |
| `docker-compose.yml` | 容器化部署 | DevOps |
| `*.sql` + `migration` | 数据库脚本 | DBA |

## 工作流

```
┌─────────────────────────────────────────────────────────────┐
│ Step 1: 项目发现（自动扫描）                                  │
│ - 扫描当前目录及子目录                                        │
│ - 识别项目类型和路径                                          │
│ - 构建项目清单                                                │
└─────────────────────────────────────────────────────────────┘
                            ↓
┌─────────────────────────────────────────────────────────────┐
│ Step 2: 需求分析（统一拆分）                                  │
│ - 一个需求 → 拆分到各项目的任务清单                            │
│ - 定义跨项目的接口契约（API 格式、数据结构）                    │
│ - 确定实现顺序（谁先谁后）                                    │
└─────────────────────────────────────────────────────────────┘
                            ↓
┌─────────────────────────────────────────────────────────────┐
│ Step 3: 架构审查（跨项目视角）                                │
│ - 审查接口契约（请求/响应格式）                                │
│ - 审查数据流（前端 → API → 数据库 → 返回）                    │
│ - 审查依赖关系（会不会互相阻塞）                               │
└─────────────────────────────────────────────────────────────┘
                            ↓
┌─────────────────────────────────────────────────────────────┐
│ Step 4: 并行实现（各项目独立 Agent）                           │
│                                                              │
│  ┌──────────┐  ┌──────────┐  ┌──────────┐                   │
│  │ 项目 A    │  │ 项目 B    │  │ 项目 C    │                  │
│  │ Agent     │  │ Agent     │  │ Agent     │                  │
│  └──────────┘  └──────────┘  └──────────┘                   │
│                                                              │
│  每个 Agent：                                                │
│  - 读取接口契约                                              │
│  - 实现本项目的代码                                          │
│  - 输出变更清单                                              │
└─────────────────────────────────────────────────────────────┘
                            ↓
┌─────────────────────────────────────────────────────────────┐
│ Step 5: 集成验证（接口对接检查）                               │
│ - 检查各项目的接口实现是否符合契约                             │
│ - 检查数据格式是否一致                                        │
│ - 检查错误处理是否完整                                        │
│ - 输出集成测试清单                                            │
└─────────────────────────────────────────────────────────────┘
                            ↓
┌─────────────────────────────────────────────────────────────┐
│ Step 6: 最终审查（整体验证）                                  │
│ - 各项目构建检查                                              │
│ - 整体功能验证                                                │
│ - 确认可以提交                                                │
└─────────────────────────────────────────────────────────────┘
```

## 接口契约优先原则

跨项目开发的核心是**接口契约**，不是实现细节。

### 接口契约的作用

1. **解耦** — 各项目可以独立开发，只要遵守契约
2. **并行** — 前后端可以同时开发，不用等对方完成
3. **测试** — 可以用 mock 数据测试，不依赖真实接口
4. **文档** — 接口契约就是最好的 API 文档

### 接口契约的生命周期

```
需求分析 → 定义接口契约 → 架构审查 → 各项目实现 → 集成验证
```

## Agent 调度方式

### 方式 1：Skill + Subagent（推荐）

```javascript
// 自动发现项目
const projects = await agent('扫描当前目录，识别项目类型和路径')

// 需求分析
const requirements = await agent('需求分析师', { 
  prompt: `根据需求拆分任务到各项目：${projects}` 
})

// 并行实现
await parallel(
  projects.map(p => () => agent(`${p.type}实现者`, { 
    prompt: `实现项目 ${p.path} 的任务` 
  }))
)

// 集成验证
await agent('集成审查员', { prompt: '检查接口对接' })
```

### 方式 2：手动调度

你说"跨项目开发xxx功能"，我自动扫描目录 → 拆分任务 → 并行实现。

## 常见跨项目模式

### 模式 1：前后端联动

```
需求：添加一个设备管理页面

拆分：
- 后端：新增 /api/equipment CRUD 接口
- 前端：新增设备管理页面 + API 调用

接口契约：
- GET /api/equipment/list → 设备列表
- POST /api/equipment → 新增设备
- PUT /api/equipment/{id} → 更新设备
- DELETE /api/equipment/{id} → 删除设备
```

### 模式 2：Web + WPF 联动

```
需求：设备数据采集功能

拆分：
- Web 后端：新增数据接收 API
- WPF 客户端：实现数据采集 + 上报

接口契约：
- POST /api/collect/data → 上报采集数据
- 批量上报格式：{ deviceId, timestamp, values: [] }
```

### 模式 3：多服务联动

```
需求：订单处理流程

拆分：
- 订单服务：创建订单
- 库存服务：扣减库存
- 支付服务：处理支付

接口契约：
- 事件驱动：OrderCreated → 库存扣减 → PaymentProcessed
```
