# 审查审计机制

## 审查层次

```
┌─────────────────────────────────────────────────────────────┐
│ Level 1: 自动审查（每次代码变更）                              │
│ - Agent 自检清单                                             │
│ - 规格审查员检查需求符合度                                    │
│ - 代码质量审查员检查代码质量                                  │
└─────────────────────────────────────────────────────────────┘
                            ↓
┌─────────────────────────────────────────────────────────────┐
│ Level 2: 流程审查（每个工作流完成）                            │
│ - 检查工作流是否按步骤执行                                    │
│ - 检查是否有遗漏的 Agent                                      │
│ - 检查输出格式是否正确                                        │
└─────────────────────────────────────────────────────────────┘
                            ↓
┌─────────────────────────────────────────────────────────────┐
│ Level 3: 周期审计（每周/每月）                                │
│ - 回顾工作流执行情况                                          │
│ - 分析常见问题和改进点                                        │
│ - 更新工作流配置                                              │
└─────────────────────────────────────────────────────────────┘
```

---

## Level 1: 自动审查

### Agent 自检清单

每个 Agent 完成任务后，必须自检：

**实现者自检**
- [ ] 依赖注入是否注册？
- [ ] 接口返回格式是否统一？
- [ ] 异步方法是否正确使用？
- [ ] 是否有 N+1 查询风险？
- [ ] 公司源码是否用 PowerShell 读取？

**审查员自检**
- [ ] 是否检查了所有需求点？
- [ ] 是否标注了严重级别？
- [ ] 是否给出了具体文件和行号？
- [ ] 是否有修复建议？

### 规格审查

**检查项：**
- 需求中的功能点是否都实现了？
- 是否有多余的功能（过度实现）？
- 验收标准是否满足？

**不通过处理：** 返回实现者修复，重新审查

### 代码质量审查

**审查视角：** Staff Engineer

**检查维度：**
1. **生产环境优先** — 想象凌晨 3 点跑着，没人看监控
2. **数据流追踪** — 从输入到输出完整走一遍
3. **并发假设** — 两个请求同时到达同一行代码
4. **防御性编程** — 每个外部输入都不可信

**严重级别：**
- **CRITICAL** — 生产必炸（数据丢失、安全漏洞、死锁）
- **HIGH** — 很可能出问题（未处理异常、资源泄漏）
- **MEDIUM** — 可能出问题（边界条件、性能隐患）
- **LOW** — 代码质量（命名、冗余、可读性）

## Level 2: 流程审查

### 工作流执行检查

每个工作流完成后，检查：

**功能开发流程**
- [ ] 需求分析师是否产出需求文档？
- [ ] 架构师是否审查技术方案？
- [ ] 实现者是否按顺序实现？
- [ ] 规格审查员是否检查需求符合度？
- [ ] 代码质量审查员是否检查代码质量？
- [ ] 最终审查员是否确认可以提交？
- [ ] 输出格式是否正确？

**Bug 修复流程**
- [ ] 调试专家是否定位根因？
- [ ] 实现者是否最小改动修复？
- [ ] 代码质量审查员是否检查修复质量？

**性能优化流程**
- [ ] 性能工程师是否先测量？
- [ ] 实现者是否针对性优化？
- [ ] 性能工程师是否复测验证？

### 流程审查报告

```markdown
# 流程审查报告

## 工作流
[工作流名称]

## 执行情况
- 触发词: [用户输入]
- 执行步骤: [实际执行的步骤]
- Agent 数量: [调用的 Agent 数量]

## 检查结果
- [ ] 需求分析完成
- [ ] 架构审查完成
- [ ] 代码实现完成
- [ ] 代码审查完成
- [ ] 最终验证完成

## 问题
- [发现的问题]

## 改进建议
- [改进建议]
```

## Level 3: 周期审计

### 每周回顾

**回顾内容：**
- 本周执行了哪些工作流？
- 哪些工作流执行顺利？
- 哪些工作流有问题？
- 常见问题是什么？

**分析维度：**
- 工作流使用频率
- Agent 调用成功率
- 审查通过率
- 常见问题类型

### 每月改进

**改进内容：**
- 更新工作流配置
- 优化 Agent 角色定义
- 完善审查清单
- 更新文档

**改进流程：**
1. 收集问题和反馈
2. 分析根本原因
3. 设计改进方案
4. 实施改进
5. 验证效果

### 审计报告模板

```markdown
# 周期审计报告

## 审计周期
[YYYY-MM-DD] 至 [YYYY-MM-DD]

## 工作流执行统计
| 工作流 | 执行次数 | 成功率 | 平均耗时 |
|--------|---------|--------|---------|
| 功能开发 | 10 | 90% | 30min |
| Bug 修复 | 5 | 100% | 15min |
| 性能优化 | 2 | 100% | 45min |

## Agent 调用统计
| Agent | 调用次数 | 通过率 | 常见问题 |
|-------|---------|--------|---------|
| 需求分析师 | 10 | 100% | - |
| 架构师 | 10 | 90% | 风险评估不准 |
| 实现者 | 10 | 85% | DI 注册遗漏 |

## 常见问题
1. [问题描述]
2. [问题描述]

## 改进措施
1. [改进措施]
2. [改进措施]

## 下周计划
- [计划]
```

## 自动化审查工具

### Workflow 工具

使用 Workflow 工具实现自动化审查：

```javascript
// 流程审查
await workflow('review-workflow', {
  checkList: [
    '需求分析完成',
    '架构审查完成',
    '代码实现完成',
    '代码审查完成',
    '最终验证完成'
  ]
})

// 周期审计
await workflow('periodic-audit', {
  period: 'weekly',
  metrics: ['成功率', '耗时', '通过率']
})
```

### 审查脚本

```powershell
# 检查 CLAUDE.md 是否存在
if (Test-Path "C:\Users\admin\.claude\CLAUDE.md") {
    Write-Host "✅ 全局 CLAUDE.md 存在"
} else {
    Write-Host "❌ 全局 CLAUDE.md 不存在"
}

# 检查文档目录
if (Test-Path "C:\Users\admin\.claude\docs") {
    $files = Get-ChildItem "C:\Users\admin\.claude\docs" -Recurse
    Write-Host "✅ 文档目录存在，包含 $($files.Count) 个文件"
} else {
    Write-Host "❌ 文档目录不存在"
}
```

## 审查审计的意义

1. **质量保证** — 确保每个工作流都按标准执行
2. **问题发现** — 及时发现和解决问题
3. **持续改进** — 不断优化工作流和 Agent
4. **知识沉淀** — 记录经验和教训
5. **可追溯性** — 有完整的审查记录
